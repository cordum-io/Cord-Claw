# CordClaw shadow metric cardinality decision

Status: accepted 2026-04-28
Task: task-9e90ab24

## Context

Shadow mode lets operators stage stricter `enforce:false` rules without
changing the real safety decision. A broad rule can match every OpenClaw action
on a daemon that is already processing hundreds or thousands of checks per
second. If `rule_id` were exported as a Prometheus label on
`cordclaw_shadow_events_total`, a single misconfigured or generated rule set
could create an unbounded number of time series.

That cardinality risk is not hypothetical: rule ids are operator-controlled
configuration, can change during rollout, and may be generated by pack tooling.
Prometheus labels should stay bounded by deployment contracts; `rule_id` is not
bounded by the CordClaw daemon.

## Decision

CordClaw will **keep cordclaw_shadow_events_total UNLABELED**.

Per-rule shadow visibility is delivered through Cordum jobs, not through
Prometheus labels:

- Per-event shadow jobs use topic `job.openclaw.shadow` and carry the full
  shadow envelope, including `rule_id`, `would_decision`, `would_reason`,
  `hook_name`, and mapped topic.
- Per-rate-limit-window summary jobs use topic
  `job.openclaw.shadow_rate_limit_summary` and carry
  `labels.cordclaw.rule_id`, `labels.denied_count`, and
  `labels.window_start`.

Prometheus remains the aggregate alerting surface. Cordum jobs are the durable
per-rule forensic surface.

## How operators get per-rule visibility

Use Prometheus to detect that shadow-mode activity is happening:

```promql
rate(cordclaw_shadow_events_total[5m])
```

Use Cordum jobs to identify the rules involved:

1. Open Cordum's `/govern/jobs` page or query the jobs API.
2. Filter to topic `job.openclaw.shadow` for per-event samples.
3. Filter to topic `job.openclaw.shadow_rate_limit_summary` for coalesced
   per-rule overflow counts.
4. Group or search by `labels.cordclaw.rule_id`.
5. Sort summary jobs by numeric `labels.denied_count` and align
   `labels.window_start` with the Prometheus spike.

This mirrors the per-agent pattern documented in
[`rate-limit-metrics.md`](rate-limit-metrics.md): aggregate metrics for alerting,
jobs for high-cardinality forensic dimensions.

## Alternatives considered

### Raw `rule_id` label

Rejected. A raw `rule_id` label is easy to query, but it is explicitly
unbounded cardinality. A noisy ruleset, generated ids, or malicious churn would
create an unbounded number of Prometheus time series.

### Bounded top-K metric

Rejected for v1. A bounded top-K export such as
`cordclaw_shadow_events_top_total{rule_id=...}` can be cardinality-safe only
with an eviction policy, a cap, and operator semantics for dropped rules. The
existing Cordum jobs path already provides exact per-rule visibility without a
new metric state machine.

### Per-rule histogram with registration cap

Rejected for v1. A capped per-rule histogram has the same eviction and
operator-interpretation complexity as top-K labels, while also multiplying
series per rule by histogram bucket count. It does not improve on durable job
records for incident response.

## Forward-compat migration path

Raw `rule_id` labels remain forbidden. If per-rule Prometheus visibility ever
becomes a hard requirement, the safe migration path is a bounded top-K metric
with TTL eviction, not an unbounded label.

That design must mirror the existing rate-limit emitter lifecycle in
[`daemon/internal/ratelimit/emitter.go`](../../daemon/internal/ratelimit/emitter.go):

- hard cap on exported rule ids;
- normalized rule-id keys;
- inactive-entry TTL eviction aligned with the emitter's one-hour
  `agentEntryTTL` pattern;
- tests proving evicted rules no longer consume metric cardinality;
- operator docs explaining top-K truncation, eviction, and how to fall back to
  Cordum jobs for complete data.

The unlabeled aggregate `cordclaw_shadow_events_total` must remain available
even if a future bounded top-K metric is added.

## Regression tripwire

The existing regression tests intentionally assert literal unlabeled metric
samples. The planning reference calls these tripwires
`daemon/internal/server/server_test.go:157 + 215`; in the current checkout, the
literal assertions are at:

- `daemon/internal/server/server_test.go:190`:
  `cordclaw_shadow_events_total 10`
- `daemon/internal/server/server_test.go:248`:
  `cordclaw_shadow_events_total 1`

Any future change that emits `cordclaw_shadow_events_total{rule_id=...}` instead
of the unlabeled sample should break those checks. Keep that failure; it is the
guardrail for this decision.

## Coordination with task-fc766e2a

The task rail asks this decision to coordinate with `task-fc766e2a` if per-rule
visibility is better surfaced through Cordum jobs instead of metrics. A Moe
search for `task-fc766e2a` in project `proj-d4db941f` returned no visible task
at the time this ADR was written.

The design conclusion does not depend on that task being visible: per-rule
visibility belongs in Cordum jobs (`job.openclaw.shadow` and
`job.openclaw.shadow_rate_limit_summary`) because jobs are durable, queryable,
and allowed to carry high-cardinality identifiers such as rule ids.
